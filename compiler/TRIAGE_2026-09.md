# Motoko compiler issue triage — September 2026

Issue #31. The maintainer track needs current, reproducible upstream work. This
is a snapshot of the open issues on `caffeinelabs/motoko`, taken on
2026-09-25 JST: nine reproduction notes, and three contribution candidates
chosen from them.

**Read-only.** Everything here came from reading the public repository and
running released compilers locally. Nothing was posted, reacted to or filed
upstream. The stale and duplicate observations below are suggestions for
whoever takes this further, worded so they can be offered to the maintainers
as they are.

## What was compared

| Compiler | Where from | Role |
| --- | --- | --- |
| moc **1.11.1** | the kit's pinned toolchain (`mops toolchain bin moc`) | what this kit builds with |
| moc **1.16.1** (2026-09-16) | `motoko-Linux-x86_64-1.16.1.tar.gz` from the GitHub release | latest release |
| `master` | **not built** | see the caveat |

**Release vs master caveat.** The rubric asks for current master status. This
pass did not build master. That takes the Nix toolchain and substantially more
time than the pass allowed, and it was deferred rather than faked. As a
partial substitute, the changelog's unreleased `## Next` section was read for
anything touching the reproduced bugs, and nothing does. A result below that
says "reproduces on 1.16.1" therefore means exactly that, and it should be
confirmed on master before it is offered upstream. A result that says "does
not reproduce" is stronger: if the latest release is fixed, master almost
certainly is too.

Platform: Linux x86_64 only. The rubric's Linux/macOS comparison was not
possible on this machine.

## Reproduction notes

Each repro is a file in [`repros/triage-2026-09/`](repros/triage-2026-09/),
adapted to current Motoko where the original no longer parses (`persistent`
actors, `mo:core` instead of `mo:base`). The adaptations are noted. To
reproduce:

```bash
node compiler/repros/triage-2026-09/run.mjs <moc> [<another moc> ...]
```

`run.mjs` runs every repro through `--check`, `-r` (the interpreter) and `-c`
(compile), and prints the exit status and the telling line. The results below
are identical on 1.11.1 and 1.16.1 unless stated.

### Still reproduces

**1. #3464: Float literal above `1.79e308` crashes the front end.**
`FloatLiteralOverflow.mo`. `--check`, `-r` and `-c` all exit 2 with
`OOPS! You've triggered a compiler bug`. The literal `179…0` (309 digits) is
accepted and `180…0` crashes. Expected: a diagnostic ("literal out of range
for type Float"), or IEEE rounding to infinity. Rubric: diagnostics, P2 (a
crash on unusual input, not a miscompilation). Next action: **test ready**.

**2. #3819: `await async { trap }` fails the IR type check.**
`AwaitNone.mo`. The original used `mo:base/Debug`; this uses `Prim.trap`.
`--check` and `-r` accept the program, and `-c` exits 1 with `IR type error
[M0000], subtype violation`. The block's type is `None`, and async lowering
builds a continuation the IR checker rejects. Rubric: codegen (async
lowering), P2. Probably the same root cause as **#4578** (see below). Next
action: **needs reproduction on master**, then patch.

**3. #4701: Float literal patterns are accepted and not compiled.**
`FloatPattern.mo`. `--check` and `-r` accept it, and the interpreter matches
`0.0`. `-c` exits 0 but prints `compile_lit_pat: (FloatLit 0)`: the backend
has no case for it, and per the issue the compiled code traps with
`TODO: compile_lit_pat`. Rubric: codegen, P1 (the type checker accepts a
program the backend cannot compile). Next action: **needs spec decision**
(reject Float patterns, or implement them), then test ready.

**4. #2017: an object body may end in a non-unit expression.**
`ObjectTerminalValue.mo`. `object { 666 }` is accepted with only an
unused-identifier warning for the binding. Rubric: type checker, P3
(consistency, not unsoundness, as the issue says). Next action: **needs spec
decision**.

### Changed or no longer reproduces

**5. #3624: top-level `await` no longer crashes codegen, but `--check` and
`-c` disagree.** `TopLevelAwait.mo`. The original crash
(`Assert_failure codegen/compile.ml`) is gone on both releases. `-c` now
rejects the program cleanly with `type error [M0038], misplaced await`.
However, `--check` exits 0 and `-r` runs the program. A check that passes on
a program the compiler rejects is a smaller bug of its own. Suggested
upstream framing: "the crash in the title appears fixed; the remaining
difference is `--check` vs `-c` on M0038". Next action: **retitle or
close-and-refile**, which is the maintainers' call.

**6. #3993: `or` patterns over variants.** `OrPatterns.mo`. The unannotated
form from the issue, `func three(#a () or #b () or #c ())`, is now rejected
up front with `M0184, cannot infer the type of this or-pattern, please add a
type annotation`. The annotated forms, a `switch` arm and a parameter
pattern, compile and run. The IR type error in the issue does not reproduce.
Suggested framing: "could not reproduce on 1.16.1; the unannotated form now
gets M0184". **Candidate for closing.**

**7. #3117: `_motoko_async_helper` clashes with the generated method.**
`AsyncHelperName.mo`. It compiles, and the Wasm exports both
`canister_update _motoko_async_helper` (the user's) and
`canister_update __motoko_async_helper` (the compiler's, now double
underscore). The clash the issue describes is resolved by the issue's option
2. The open design question is whether to reserve the `__` prefix for users.
**Candidate for closing or narrowing.**

**8. #4733: "cannot infer type of forward variable" with a destructured
import.** `ForwardImport.mo`. Current releases require `persistent`, so the
repro is a `persistent actor class`, which compiles and interprets without
M0055. Adding `persistent` did not change the shape the issue blamed (the
last declaration of the class body). **Candidate for closing**, with a note
that the non-persistent form now stops at M0220 before reaching that code.

**9. #3855: duplicate deprecation warnings.** `DeprecationTwice.mo`, with
`mo:core`'s deprecated `Blob.fromArray` standing in for base's `Hash.hash`.
Two uses give exactly two M0154 warnings, one each, and the inferred use no
longer warns twice. **Candidate for closing**, with the caveat that base was
not tested.

The kit's own upstream finding stays tracked separately as local issue #42,
with its repro in [`repros/envvar-rope/`](repros/envvar-rope/README.md).

## Duplicates and stale issues

These are observations to offer, not conclusions. Only the maintainers can
close anything.

- **#3819 and #4578** both report the IR checker rejecting a continuation
  whose argument type is `None` after async lowering (`None -> ()` against
  `() -> ()`). They probably share a root cause and could be linked. They
  should not be closed as duplicates until one fix is shown to resolve both.
- **#3993, #3117, #4733, #3855** do not reproduce on 1.16.1 as written
  (notes 6–9). Each deserves a short comment with the repro and the
  compiler version before anyone proposes closing it.
- **#3624** is fixed as titled but has a residual issue (note 5).
- 33 open issues have not been touched since before 2025. They are listed by
  the same `gh api` query this snapshot used (`state=open`, pull requests
  filtered out, `updated_at < 2025-01-01`) and were not individually
  reviewed. Reviewing them is itself a good first contribution.

## Three contribution candidates

Chosen for a first contributor: small, testable in the existing suites, and
touching one pass each. Test directories are the upstream layout (`test/fail`
for expected diagnostics with `.ok` expectations, `test/run` for
interpreter-and-compiler runs).

| | Candidate | Scope | Test location | Risk |
| --- | --- | --- | --- | --- |
| A | **#3464: turn the Float-literal OOPS into a diagnostic** | the literal check in the front end (`mo_frontend/typing.ml`, `check_lit_val` in the issue's backtrace): catch the failed conversion and report an out-of-range literal, as integer literals already do | `test/fail/float-literal-overflow.mo` + its `.tc.ok` | **Low.** Front end only, and a crash becomes an error. The only decision is error versus IEEE rounding to infinity, and matching how other out-of-range literals behave settles it. |
| B | **#3624 residual: make `--check` report M0038** | find why "misplaced await" is raised only on the compile path, and move the check where `--check` runs it | `test/fail/top-level-await.mo`, run under `--check` and `-c` | **Low.** A diagnostic moves earlier. Confirm on master first, since this came out of this triage and the upstream issue does not describe it yet. |
| C | **#4701: decide and implement Float literal patterns** | either reject Float literal patterns in the type checker (a new error code), or add the `FloatLit` case to the backend's `compile_lit_pat`, comparing with `f64.eq` | `test/run/float-pattern.mo` (interpreter and compiled must agree) or `test/fail/…` if rejected | **Medium.** It needs a spec decision first. IEEE equality makes `-0.0` match `0` and `NaN` match nothing, and the interpreter's current behaviour has to be the same. Ask before writing code. |

Not chosen, though real: **#3819/#4578**. The fix lives in async lowering and
the IR checker, and is a poor first patch for someone who does not yet know
those passes. It is a good second one.

## Method, for the next snapshot

```bash
gh api --paginate 'repos/caffeinelabs/motoko/issues?state=open&per_page=100' \
  --jq '.[] | select(.pull_request|not) | [.number, .created_at[0:10], .updated_at[0:10], .comments, ([.labels[].name]|join(",")), .title] | @tsv'
```

Then read the bodies of the bug-labelled, `typing` and `error-messages`
issues. Keep the ones with a self-contained snippet, adapt each snippet to
current Motoko, and add it to `repros/triage-YYYY-MM/`. Record what changed
in the adaptation, run `run.mjs` against the pinned and the latest compiler,
and write down only what the output shows.
